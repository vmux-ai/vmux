# Agent Instructions

Use caveman mode: terse, direct, no filler. Execute first, then report.

## Design

- Start at `docs/README.md`. Read the relevant UX topic, `docs/dx/architecture.md`, and `docs/dx/feature-development.md` before changing behavior or boundaries. Code, tests, typed contracts, and `feature.ron` remain authoritative.
- Keep docs under `docs/ux/` and `docs/dx/`, with `docs/README.md` as the entry point. Update UX guidance when observable user behavior changes. Document durable expectations; leave implementation details and debugging history in code and tests. Do not add specs, plans, dated records, or documentation generators. Relay internals belong to `vmux-cloud`.
- Do not change `docs/dx/architecture.md` for small refactoring issues, routine ownership migrations, renames, helper extraction, bug fixes or validation changes unless the user explicitly requests it. Reading architecture guidance does not require editing it. Update the guide only for substantial changes to system responsibilities, dependency direction or shared ownership/lifecycle boundaries. Rewrite the relevant overview; never append per-PR migration notes, type/field inventories, system ordering or cache mechanics. `docs/architecture.md` remains a compatibility pointer; do not append implementation notes there. Existing types, contracts, tests and ownership metadata carry those details.
- Before implementation, carry the Linear issue beyond UX/acceptance criteria: name crates and dependency direction, root/child plugins and their composition, entities/components/ownership, contracts and sender/receiver, systems and ordering, persistence/adapters, and the end-to-end success/failure/cancellation/retry/rollback/approval flow. Use concrete proposed type/module names. Reject cycles and ownership leaks; distinguish settled decisions, open questions, and non-goals. Update the issue when design changes.
- For UI, specify typed `UiState` snapshots/patches and `#[vmux_api::ui_event]` payloads, their fields, source entity, projection, sender, and receiver. State carries current values, events carry intent, and versioned effects carry one-shot DOM behavior.
- When taking a Linear issue, move it to **In Progress before any other work**.

## Rust and modules

- Prefer imperative control flow, early returns, `match`, and explicit loops. Small local conversions/defaults are fine; avoid long combinator chains and closures that assemble state.
- Put behavior on its owning type. Exceptions: framework entry points and a private helper used once by the item above it. Fixtures follow the same rule; a constructor wrapper should be the constructor. Do not nest functions or export loose functions for another module to orchestrate.
- No Rust comments (`//`, `///`, `//!`) outside vendored `patches/`. Put durable architectural reasons in the relevant DX topic.
- No vmux-owned `macro_rules!`, function-like procedural macros, or custom derives. Attribute metadata/framework integration and framework/serialization derives are allowed; vendored code and Rust-required tuple-arity generation are exceptions.
- Put entry points first, followed by their composed children. Separate declarations with bodies by one blank line; keep imports, attributes, and bodyless declarations together.
- Crates belong in `crates/app/` (user-started products), `crates/feature/` (user-facing capabilities/pages plus their domain/UI/host behavior), or `crates/util/` (reusable infrastructure/composition). The `host` cfg alias describes compiled code, not directory placement.
- Use filename modules, never `mod.rs`. A module directory needs at least two children; otherwise use siblings with explicit imports.
- Plugin types use descriptive names ending in `Plugin`, such as `HttpPlugin` or `AccountPlugin`; never declare or re-export a generic `Plugin` type. This includes private, platform, DX, and test plugins. The Bevy `Plugin` trait keeps its framework name.
- Other names should not repeat their crate/module/feature/owner except to prevent a shared or serialized boundary collision. Reserve `Chrome` for Chrome/Chromium compatibility. Replace generic vmux `Action` vocabulary with `Request`, `Operation`, `Effect`, or a domain noun; externally fixed vocabulary and standard domain terms such as LSP `CodeAction` are exempt at their boundaries and translated into vmux-owned state.
- Never commit `.claude/*`, `Co-Authored-By`, or `Generated by` trailers.

## ECS

- Give every vmux-owned declaration and behavior one actual ECS owner or a documented external adapter. This applies inside feature crates, app/util code, UI, tests/examples and vmux-owned patch changes. A name, directory, immutable temporary model, wrapper, or unused ECS derive is not ownership.
- Keep domain decisions, reconciliation, selection, queues and state transitions in the owning components and registered systems. Do not embed an independently addressed registry, boxed business engine or workflow graph inside one aggregate Component/Resource. Resources own truly global facts; indexes are derived from canonical entities.
- Materialize native/provider input into canonical ECS before domain consumers use it. Adapters translate external formats or perform bounded IO; they do not retain parallel normalized state or choose vmux behavior. UI contracts are one-way projections and typed intent, never a second mutation authority.
- Plain nested values need a concrete canonical owner. Plain adapters need an item-specific record in their crate's `ecs-policy.ron` identifying the external interface, canonical input/output, scope/lifetime and cancellation/eviction, with a reference to the existing architecture boundary. Updating that record does not require new architecture prose; change the guide only for a substantial architectural decision. Website, script, and shared build-helper records live in those subsystems. The root policy holds only immutable historical and upstream references. Never add a wildcard exception or treat deterministic domain logic as external conversion.
- Run the ownership policy gate when changing declarations or boundaries. Frozen legacy entries are migration debt: verify their historical provenance, remove them when changed/deleted, and never enlarge or refresh the baseline to approve new code. Each owner migration removes its entries; VMX-253 ends only after the final audit accounts for all remaining declarations.
- Compose entities from shared `Name`, IDs, `Active`, `Order`, and timestamps before adding feature markers. Do not duplicate shared fields in aggregate components or rows. Resources are for truly global state.
- Keep systems/observers private to their registering plugin. Name them by the local operation (`load`, `sync`, `remove`; optional `on_`), without owner or `system`/`plugin`/`feature` suffixes. Tests add the production plugin instead of exporting/registering its private systems.
- Use typed systems/messages for cross-module behavior. Register messages, run production schedules, and assert observable ECS results.
- Independent domain commands use concrete typed Messages or EntityEvents. Do not multiplex unrelated commands through a retained Request/Work/Action/Operation enum or combine separate workflows in one phase enum. Accepted work remains on its operation entity. An ordered external-adapter ingress stream (`vmux_channel::AsyncChannel<E>` / `MessageChannel<E>`) may carry a foreign-boundary payload enum that is unpacked at the ingress boundary into canonical ECS state/events. Every other production enum needs an exact reviewed purpose: a canonical scalar/phase, read-only projection, typed UI encoder, or actual foreign boundary. Message derives and generic dispatch helpers do not establish that purpose.
- I/O is not a blanket enum exception. General process/filesystem command and result unions use concrete job/result types; a signal, Component or Job enum can claim a boundary purpose only with actual foreign-format evidence and an exact reviewed interface. Serializer/ABI metadata is necessary evidence for that discriminator, never sufficient approval by itself.
- Registered systems and production behavior functions/methods have a default maximum of 100 source lines containing code tokens. Blank/comment/test-only lines do not count; moving behavior into a SystemParam, trait, closure or macro does not evade the limit. Verified Dioxus renderers and pure Bevy plugin installation are outside this behavior budget. Other mechanical IO/compiler bodies need an exact reviewed boundary exception. Frozen `shape.debt` is migration work, never an exception: remove it when changed/deleted, never restore retired entries or enlarge/refresh its fixed Git baseline.
- Split plugins by independently configurable, reusable, platform, or lifecycle boundaries, not by item kind. Fewer than four closely coupled systems normally stay with their owner; smaller plugins need an independent composition or scheduling boundary. Prefer entity state, targeted observers, and owner methods over micro-plugins or `App` extensions.
- Gate platform imports/APIs and compose platform plugins separately. macOS is primary; Linux builds/tests in CI.
- Use cohesive `SystemParam` capabilities for readability or parameter limits, at the narrowest visibility. Their methods may perform synchronous lookup, validation, selection, and scoped mutation. Keep request iteration, transitions, async ownership, multi-feature dispatch, and ordering in systems; avoid grab bags, hidden state, and large `run`/`handle`/`dispatch` facades. Inline one-off parameters without cohesive behavior.
- Chain consecutive `App` builder calls. Keep `world()`, `world_mut()`, `update()`, and conditional mutations separate.
- Never use `UpdateMode::Continuous`. Use reactive modes and route missing wakes through `EventLoopProxy::send_event(WinitUserEvent::WakeUp)`; preserve CEF wake throttling.

## UI

- Localize new user-facing strings through Fluent (`vmux_ui::i18n`) in every bundled locale, with matching IDs/variables. No untranslated literals or English fallback; external content and raw diagnostics are exempt.
- Use skeletons or matrix rain instead of literal loading text. Layout, selection, focus, and routing respond in the input frame; do not wait for data, page readiness, fonts, or timers. Reserve loading geometry, preserve scroll/positions, and place initial transcripts before revealing messages.
- Use themed page surfaces; pure black/white are reserved for media, QR codes, and scrims. Prefer flat hierarchy over decorative borders/shadows.
- Anything returning `Element` is a PascalCase `#[component]`, rendered as `Foo { .. }`, with owned props. Do not inline plain `Element` helpers.

## Validation

- Add targeted tests only for plausible regressions or explicit policies, with an independent oracle that survives behavior-preserving refactors. Prefer contracts, state transitions, persistence, typed ECS integration, and packaging behavior. Important UI tests inspect DOM/computed state/interaction/visual output.
- Do not test CSS literals, constructor fields, constants, enum payloads, derived defaults, framework behavior, or implementation shape. Source scans are limited to explicit repository/packaging policies that cannot be tested behaviorally; name the protected invariant.
- Avoid duplicate coverage and silently missing fixtures. Use exact-set/table-driven registry checks. Keep unit tests inline; split only reusable integration harnesses, not to reduce line count. Production size audits exclude `#[cfg(test)]`.
- Install `vmux internal setup-hooks` in every worktree after preparing the development CLI. The pre-push hook checks Rust formatting without compiling or requiring a prepared CLI. CI owns Clippy, DX lifecycle/CLI tests, repository policy/conventions tests, and platform validation. Use targeted tests and Clippy when the changed behavior warrants them; run workspace-wide local checks only when requested. `vmux dx test` remains an explicit diagnostic command. Fix known failures before committing/pushing and require successful CI on the latest head before merging; never claim a check passed unless it ran.
- For CI workflow, test-fixture, and declaration-free fixes, reproduce the failed case with the CI features and relevant environment, run the affected regression tests, and push once those checks and formatting pass. Do not hold an otherwise validated feature push for optional Clippy, full-workspace tests, or full convention scans; CI owns those merge gates. Still run an ownership gate when declarations or boundaries change, and never push a known failure.
- After resolving conflicts, validate the affected code and policy records. A clean rebase of already validated code does not by itself require repeating full-workspace local checks. Report the pushed head and monitor its CI instead of ending at "ready to push."
- Never run concurrent Cargo/build/test commands against the same target. Run workspace-wide local checks only when the user asks.

## Builds and debugging

- Agents never launch or automate the app. Use `vmux build <branch>` for iteration; it builds/signs without launching or stopping apps and uses shared CEF/Bevy runtime libraries. The user launches with `vmux run <branch>`; completed artifacts launch without compiling. Use `vmux build <branch> -p local` for packaging, permissions, and release-like checks; `-p release` prepares a release.
- Build entry points enforce target locks and storage policy; do not bypass a refusal. `vmux cache status` reports usage, `vmux cache clean` previews cleanup, and `vmux cache clean --apply` applies it under the lock. Preserve prepared binaries, runtime libraries, and distribution artifacts; verify the ready artifact/mtime and final free-space report before handoff.
- Builds share a store and Chromium profile per named profile. The user quits the previous GUI before switching; the next build drains its old daemon and waits for its lease under the GUI lock. A same-profile restart preserves background work. `vmux stop` is explicit shutdown, not an iteration step; quit legacy builds without leases before shared-data use.
- Use `VMUX_DATA_DIR=/absolute/path/to/a/copy` for persistence/schema/migrations. Never use `VMUX_TEST=1` with real shared data.
- Temporary diagnostics are unconditional tracing (`bevy::log::info!`/`warn!`), removed before commit. Raw stderr/`eprintln!` is not captured. After user reproduction, read logs yourself; never ask for pasted logs or captured stderr:
  - `~/Library/Application Support/Vmux/<build-profile>/logs/vmux-<build-profile>.<date>.log`
  - `~/Library/Application Support/Vmux/<build-profile>/profiles/<profile>/chrome_debug.log`

## Delivery

- Never edit the primary worktree or land feature work in local `main` via merge/rebase/cherry-pick. Create feature worktrees under `~/.vmux/worktrees/vmux-ai/vmux/<name>` (`git worktree add ~/.vmux/worktrees/vmux-ai/vmux/<name> -b <branch> origin/main`; use `vmx-<issue>` as `<name>` for Linear work, otherwise a feature name). Rebase onto the fetched target for updates; verify scope and use `git push --force-with-lease` for rebased PR branches. Create PRs directly with `gh pr create`, never `-w`; return the URL.
- Deliver user-facing work end to end through the product UI. Stack only for a real dependency on an unmerged PR, name that dependency, and keep each PR coherent rather than splitting implementation layers.
- Implementation agents finish self-review, targeted local validation, the formatting pre-push hook, applicable manual QA, and unused task-cache cleanup before handoff. Heavy checks run in CI rather than being repeated locally. One user-designated integration agent then owns accepted QA-complete PRs through review/CI fixes, latest-head checks, squash merge, and cleanup; other agents leave accepted branches to that owner. Such a handoff authorizes feature pushes and squash merge into the stated target after findings are addressed/triaged and all applicable checks pass; honor holds, scope changes, and runtime approvals without repeated permission questions.
- Before QA, self-review the entire diff against the fetched target, including new files, callers/tests, ownership, persistence, platform/security boundaries, and failure/cancellation paths. Fix findings and repeat affected checks/QA when later changes invalidate them; passing tests alone is not self-review.
- Manual app QA is performed by the user; agents prepare artifacts and inspect logs. Record the result/artifact, or a concrete reason QA is not applicable for infrastructure-only work.
- Handoff includes PR URL/target/approved head; feature branch and all primary/review/integration/QA worktree paths; every external temporary `CARGO_TARGET_DIR` (including `/tmp`); check commands/results/counts and Clippy/hook status; self-review findings/disposition; QA result; remaining CI/reviews and retained storage/release conditions.
- Before merging, review all feedback and verify applicable checks on the latest head. Report triage in chat; post replies or resolve threads only when explicitly requested. Record the approved head used for the merge.

## Cleanup after merge

The integration agent owns cleanup until verified; retained task storage means **cleanup pending**, not task complete.

1. Confirm GitHub merged the recorded approved head and each local head has landed. Inventory all handoff worktrees/temporary targets and each repository's own registrations before deleting any checkout.
2. Retain dirty/unpublished/actively edited work, running apps/VMs, active build/test locks, and stacked PR bases. Do not stop apps to qualify for cleanup. Retarget/rebase dependents before removing a base.
3. Leave the worktree, use `git worktree remove <absolute-path>` for eligible worktrees, and remove their task-owned external compile caches. Preserve shared caches/fixtures and the primary checkout's edits. Local branch deletion requires no worktree users or unpublished work.
   - Transition rule for legacy submodule-backed `.worktrees/*` checkouts: `git submodule deinit` + `git worktree remove -f -f` is permitted only after verifying zero nested child worktrees, a clean submodule working tree, and a merged approved head.
4. Before remote branch deletion, compare `git ls-remote origin refs/heads/<branch>` with the recorded approved merge head. Delete only with an explicit `--force-with-lease=refs/heads/<branch>:<approved-head>` lease; retain and report a changed head.
5. Verify Git registrations and filesystem removal. Report removed paths and before/after `df` free space (APFS clone sizes are not additive). Keep retained paths, reasons, and release conditions on the owner's follow-up list until handled.
